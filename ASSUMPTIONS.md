# Assumptions

Things that weren't fully specified in the brief, where a safe/simple default was chosen instead of asking. Revisit any of these if they don't match reality.

## Naming / schema deviations from the brief's literal table list

- **`returns` -> `product_returns`.** `RETURNS` is a reserved word in MySQL/MariaDB (used in `CREATE FUNCTION ... RETURNS` syntax); an unquoted table named `returns` fails to create. Verified empirically against MariaDB 10.11 during this build. All FK/index names follow the new table name.
- **Two extra tables beyond the brief's minimum list**: `other_costs` (backs the "Other Variable Costs" line in the profit formula - the brief's formula needs it but the minimum table list didn't include it) and `exchange_rates` (optional reference table to source per-transaction FX rates consistently; not required for reporting since every transactional row already stores its own `exchange_rate_to_base`).
- **Shipping**: the brief's example (customer paid 3.90 EUR, carrier actually cost 5.20 EUR) is modeled as `orders.shipping_fee_charged` + `orders.actual_shipping_cost`, with a separate `shipping_costs` table holding *configurable rate rules* per method (used to estimate `actual_shipping_cost` when no real carrier invoice amount is known) - rather than a dedicated per-order shipping-cost table, since the brief's own table list only mentions `shipping_costs` (singular, rate-table shaped).
- **Cancellations**: modeled as `orders.is_cancelled` + `orders.status`, not a separate table. A paid-then-cancelled order additionally gets a `FULL` row in `refunds` so the money reversal stays auditable, per the brief's requirement that a cancelled order must not show as normal revenue.

## Technical defaults

- **Base currency**: EUR (`APP_BASE_CURRENCY` in `.env`), matching "Első verzióban EUR legyen a base currency."
- **PHP baseline**: 8.1+ syntax (readonly properties, enums-as-DB-ENUM not PHP enums, constructor promotion, `match`). Verified against PHP 8.4 in this session; cPanel accounts commonly offer 8.1-8.3 via MultiPHP Manager, so nothing 8.4-specific was used intentionally.
- **No Composer / no third-party PHP packages** in V1 - see ARCHITECTURE.md "Why no framework, why no Composer". Chart.js is loaded from a CDN in the browser, not a PHP dependency.
- **Session-only admin auth**, one role distinction (`admin` / `viewer` in `users.role`, `viewer` unused until a read-only screen is needed). No "forgot password" flow in V1 - the first admin account is created via `scripts/create_admin_user.php` from the command line.
- **Router**: exact-path + `:param` matching via `?route=` (set by `public/.htaccess`'s rewrite rule), not PATH_INFO-based - works identically whether the vhost docroot is `public/` directly or the app sits in a subdirectory.
- **Logging**: flat files under `storage/logs/{channel}-{date}.log`, not a database table (except `api_logs`/`sync_logs`, which the brief explicitly asked to be queryable from the admin UI).
- **Money formatting** in the UI uses `.` as the decimal separator and a space as the thousands separator (locale-neutral default) rather than assuming HU or SK formatting conventions - revisit once real users are testing the dashboard.

## UNAS API specifics

- Login, `/getOrder`, `/getProduct` request-side protocol (endpoints, filter fields, auth flow) were confirmed live in an earlier pass (HTTP 200 on all three) and are implemented as given.
- The response-side field mapping implemented this pass (`OrderRepository`, `ProductRepository`, `cron/sync_unas_orders.php`, `cron/sync_unas_products.php`) uses **only** field names the project owner directly reported from inspecting the real sanitized sample XML on production - not search-result summaries, not inference. See ARCHITECTURE.md "UNAS API integration status" for the exact mapping table and, separately, the explicit list of what's still unconfirmed (order line item quantity/price/discount fields, Shipping/Customer/Invoice sub-structure, which `<Param>` means "size", whether a stock field exists at all).
- **Order line items ARE now imported**, but only after the project owner directly reported the confirmed `<Item>` fields (`Sku`, `Quantity`, `PriceNet`, `PriceGross`, `Vat`, `Percent`) and, critically, that UNAS mixes synthetic financial rows (`shipping-cost`, `discount-percent`, `gift`) into the same `<Items>` list as real merchandise. See ARCHITECTURE.md "Order line item financial model" for the full mapping, the classifier, and the reconciliation mechanism. Two things in that model are inferred rather than confirmed - both called out prominently there and worth repeating: (1) `PriceGross`/`PriceNet` are treated as **per-unit**, not line-total, prices - inferred from the reconciliation formula `PriceGross * Quantity` being dimensionally meaningless otherwise, since no confirmed example had `Quantity > 1` to test directly; (2) the classifier's "looks like a synthetic slug" heuristic (lowercase-letters-and-hyphens SKU) can misclassify a hypothetical all-lowercase real merchandise SKU as synthetic - accepted because the failure mode is "excluded and logged", not "silently wrong revenue".
- **Parent/variant grouping for products**: no UNAS field was found that groups sibling SKUs (sizes) under a common real parent - the live sample showed each SKU as its own top-level `<Product>` with an empty `<Variants>` node. `ProductRepository` therefore creates a 1:1 "shadow" `products` parent per SKU (same UNAS `<Id>` on both the parent and the variant). This is provisional: if a real grouping field is found later (the account's *other* products might behave differently than the 3-record sample inspected), a follow-up migration can merge shadow parents without touching `product_variants`/`order_items`, which is what profit calculations actually key off.
- ~~`<Prices><Price type=normal><Actual>` is assumed to be the currently effective gross selling price~~ - **CORRECTED**: a production sync proved this wrong (SKU FZ4625-100-11: `Gross=189, Actual=1` was stored as `list_price=189, current_price=1`). `<Actual>` is a flag ("1") marking which `<Price>` row is currently active, never a monetary amount - `<Gross>` is always the amount, on every row. Fixed in `UnasProductPriceMapper::extractPrice()`: `current_price` reads the `<Gross>` of whichever row has `<Actual>=1`, falling back to `list_price` only when no row is flagged at all (not when a flagged row's `<Gross>` is itself malformed - that stays `null` rather than silently substituting an unrelated row's price). The ~50 products already synced with the old, wrong mapping are corrected automatically by the next idempotent product sync (upsert keyed on SKU).
- `Expire`/`ExpireTime` parsing is now confirmed and fixed: `<ExpireTime>` (UNIX timestamp) is authoritative when present, `<Expire>` (`"Y.m.d H:i:s"`, dot-separated - notably different from the `Y-m-d` used for `/getOrder` request filters elsewhere in this codebase) is the fallback. No longer a guess.
- `/getOrder`'s `DateStart`/`DateEnd` request format is sent as plain `Y-m-d` by `cron/sync_unas_orders.php` - unconfirmed, chosen as the most common convention; a wrong format will surface directly in that job's output/`sync_logs.error_message` rather than silently misbehaving (UNAS would either error or presumably ignore the filter, both observable).
- `order_adjustments.discount_total`'s sign convention: stored/reported as a **positive magnitude** (e.g. `10.90`, not `-10.90`) even though the underlying `discount-percent` `<Item>` row is negative - matches how a human would read a "Discount Total" column. `gift`/`unknown_synthetic` amounts keep their original sign in `order_adjustments.price_gross` since they aren't folded into a summary column at all yet (see ARCHITECTURE.md).
- `/getOrder`'s single-order filter field (`getOrderDetails()`, unused by the cron jobs) is still assumed to be `OrderID` - unconfirmed, unexercised.
- `/getOrder`'s pagination is still assumed to reuse `/getProduct`'s confirmed `LimitNum`/`LimitStart` convention - unconfirmed but exercised by `cron/sync_unas_orders.php`, so a live run will confirm or refute it directly.
- UNAS enforces a **requests-per-minute** rate limit (explicitly stated by the project owner); `UNAS_RATE_LIMIT_PER_MINUTE` defaults to 60 in `.env.example` as a conservative placeholder, still not independently confirmed.
- `scripts/test_unas_connection.php`'s PII redaction is tag-name-keyword-based plus an email-regex safety net, not an exact allow-list - tighten to an allow-list once the Customer/Shipping/Invoice field names are confirmed.

## Product status rules

- The brief's example thresholds (SCALE: margin > 20% and ROAS > 1.2x break-even; WATCH: margin 10-20%; STOP: ROAS < break-even; LOSS: negative contribution profit) were seeded verbatim into the `settings` table as the V1 defaults. The status **engine** itself (`ProductStatusService`) is not yet built - only its configuration storage - since it depends on ad spend data (Meta/Google, V4/V5) that V1 doesn't have yet.

## What's deliberately NOT in this codebase yet

Per "31. Első feladatod", the first pass was scoped to: structure, schema, `.env.example`, config, PDO connection, admin login, dashboard skeleton, `UnasApiService` skeleton. A second pass corrected that skeleton's protocol details and added the live diagnostic script. A third pass added confirmed order-header and product/SKU sync. This fourth pass added confirmed order line item import, synthetic-row classification, and order-total reconciliation, but deliberately still does **not** include: `cron/recalculate_profit.php` (explicitly deferred by the project owner until reconciliation is proven against real production order data, not just the synthetic test fixtures this pass validated against), FIFO consumption logic, `ProfitService`, CSV import, order pruning (an item UNAS stops returning for an order isn't removed locally on re-sync), or the Orders/Products/Inventory/Settings/Sync Logs/API Logs admin screens (nav links exist in the layout but are not yet routed - clicking them 404s). cPanel cron was also deliberately not configured this pass - both sync scripts are ready to run manually but nothing schedules them automatically yet.
